# 渠道经营分析报表合并设计

- 日期：2026-08-14
- 状态：已实现（静态原型）
- 适用范围：拾马商城平台运营后台一期静态原型
- 变更对象：`admin.html`、`docs/拾马商城后台一期PRD.md`、`tests/prototype.test.js`、`tests/visual-check.js`

## 1. 业务目标

将左侧菜单中独立的“小程序商城分析”和“API供货分析”合并成一张“渠道经营分析”报表。页面顶部通过“小程序商城客户”和“API 供货客户”两个 Tab 切换统计口径。

本次改造主要解决两个问题：

1. 消除两张结构高度重复的分析页，降低运营人员的菜单切换和认知成本。
2. 将原横向状态条升级为“订单流×资金流”双轨图，让运营人员能直接看到订单阶段与冻结、支出、出账、回款或余额校对的对应关系。

### 1.1 成功标准

- 运营人员从左侧菜单只需进入一个分析页。
- 当前客户类型在首屏顶部清晰可见，不依赖面包屑或指标文案猜测。
- 切换 Tab 后，指标、双轨图、商品排行、企业排行和导出口径全量同步切换。
- 首屏同时呈现核心指标和订单资金闭环，无需先滚动到另一个区域。
- 双轨图的异常节点同时呈现订单数和金额或积分影响，不只显示比例。

## 2. 信息架构变更

### 2.1 左侧菜单

```text
经营看板
├── 经营总览
└── 渠道经营分析
```

删除原“小程序商城分析”和“API供货分析”两个菜单项。合并页使用稳定视图标识 `channel-analysis`。

本次不合并“小程序商城客户”和“API供货客户”的业务管理菜单；客户、订单和账户操作入口仍按渠道隔离。

### 2.2 页面顶部

报表顶部按以下顺序排列：

1. 客户类型 Tab：小程序商城客户 / API 供货客户。
2. 时间筛选：今天、本周、本月；一期原型保持现有选项。
3. 导出报表。

Tab 使用客户类型全称，不使用“小程序 / API”的简写，避免与终端渠道或技术接口混淆。Tab 内辅助文案明确各自口径：

- 小程序商城客户：积分消费·采购履约·企业结算。
- API 供货客户：人民币订单·客户回款·上游校对。

## 3. 页面布局

### 3.1 首屏摘要区

首屏采用左右分栏：

| 区域 | 宽度 | 内容 | 设计意图 |
|---|---:|---|---|
| 左侧指标区 | 34% | 2 列 × 4 行的 8 张紧凑指标卡 | 保留原有全部核心口径，压缩单卡高度 |
| 右侧闭环区 | 66% | 订单流与资金流双轨图 | 保证横向阶段和竖向对应关系可读 |

当页面宽度不足以保持双轨图节点可读时，首屏摘要区改为上下排列，不压缩图表节点文案。现有后台最小宽度为 1024px，需在 1024px 和 1440px 视口验证。

### 3.2 排行区

首屏摘要区下方保留：

1. 商品销量排行。
2. 企业贡献排行。

两张表保持现有字段和排序，仅改为由当前 Tab 决定渠道口径。不把两个渠道的数据合并到同一张排行表。

## 4. Tab 交互与状态

### 4.1 默认状态

- 从左侧菜单首次进入时，默认选中“小程序商城客户”。
- 当前 Tab 只是报表查询状态，不修改客户的 `channel_type`，也不改变任何订单或结算状态。
- 一期静态原型在当前页面生命周期内保留选中的 Tab；离开页面后再进入恢复默认 Tab。

### 4.2 切换规则

点击 Tab 后一次性替换：

- 页面说明文案。
- 8 张核心指标卡。
- 双轨图的节点、数值、转化率和异常摘要。
- 商品销量排行的表头与数据。
- 企业贡献排行的表头与数据。
- 导出报表的渠道参数。

切换不修改当前时间范围，便于对照同一周期的两类客户。

### 4.3 触发条件与副作用

| 动作 | 触发条件 | 界面结果 | 业务副作用 |
|---|---|---|---|
| 切换客户 Tab | 用户点击非当前 Tab | 全页报表换为目标渠道口径 | 无 |
| 修改时间范围 | 用户选择今天/本周/本月 | 当前 Tab 数据按新周期刷新 | 无 |
| 导出报表 | 用户点击导出 | 导出当前 Tab + 当前时间范围 | 产生下载文件；静态原型仅给出成功反馈 |

## 5. 核心指标

### 5.1 小程序商城客户

1. 有效订单。
2. 结算金额。
3. 消费积分。
4. 冻结积分。
5. 采购成本。
6. 预计毛利。
7. 待企业结算。
8. 预付资金入账。

### 5.2 API 供货客户

1. 受理订单。
2. 订单金额。
3. 采购成本。
4. 采购成功率。
5. 预计毛利。
6. 客户待回款。
7. 上游账户余额。
8. 余额差异。

指标卡取消原有顶部彩色粗边，改用数字、辅助文案和仅在异常数值上使用警示色，降低首屏视觉噪音。

## 6. 订单与资金结算双轨图

### 6.1 共同结构

双轨图由五部分组成：

1. 图表标题、当前数据更新时间。
2. 上轨“订单流”，使用蓝色节点。
3. 下轨“资金流”，使用绿色节点。
4. 上下节点之间的竖向虚线和对应说明。
5. 底部异常摘要，使用橙色警示区。

节点之间的横向箭头表示统计阶段的先后关系，不表示单一订单只有一个状态。原始订单的接口受理、采购、履约、积分、结算和售后状态仍独立并行，图表只是聚合视图，不得被实现成单一订单状态机。

### 6.2 小程序商城客户节点

| 阶段 | 订单流 | 资金流 | 对应说明 |
|---|---|---|---|
| 1 | 提交订单 | 积分冻结 | 提交时冻结预计消费积分 |
| 2 | 采购成功 | 积分扣减 / 采购支出 | 采购成功后确认实际成本并进入积分扣减 |
| 3 | 履约完成 | 企业结算出账 | 按订单价格快照进入企业结算 |
| 4 | 订单完成 | 预付入账 / 后结待回款 | 按企业结算方式分流 |

异常摘要至少覆盖：已提交但未冻结、已采购但未扣减、履约完成但未出账、后结待回款。

### 6.3 API 供货客户节点

| 阶段 | 订单流 | 资金流 | 对应说明 |
|---|---|---|---|
| 1 | API 订单受理 | 余额/授信占用 | 受理时按客户结算模式占用额度 |
| 2 | 上游采购成功 | 上游采购支出 | 采购成功后记录实际采购成本 |
| 3 | 履约完成 | 客户结算出账 | 按订单价格快照计入客户账单 |
| 4 | 订单完成 | 客户回款 / 上游余额校对 | 同时展示待回款与上游理论/实际余额差异 |

异常摘要至少覆盖：受理后采购结果未知、采购失败或待重试、已完成但未出账、客户待回款、上游余额差异。

## 7. 数据与口径

### 7.1 查询参数

报表的最小查询上下文为：

```text
channel_type + date_range
```

- `channel_type=MINIAPP` 时不得返回 API 客户或 API 订单数据。
- `channel_type=API` 时不得返回积分指标或小程序客户排行。
- 报表不提供“全部渠道” Tab，跨渠道汇总仍属于“经营总览”。

### 7.2 统计规则

继续遵守现有 PRD 的报表公共规则：

- 取消订单不计入销量和结算额。
- 退款按退款确认时间冲减。
- 结算金额使用订单价格快照。
- 采购成本使用订单实际采购成本。
- 毛利额＝企业结算金额－采购成本－退款调整。
- 企业贡献占比＝企业结算金额÷当前 Tab 对应渠道结算总额。
- 两个 Tab 在相同时间范围内的合计必须与经营总览一致。

## 8. 异常和边界

| 场景 | 处理方式 | 什么情况会出问题 |
|---|---|---|
| 当前渠道无数据 | 指标显示 0，双轨图保留节点并显示“当前周期暂无数据”，排行表显示空状态 | 直接隐藏节点会让用户误以为流程不存在 |
| 部分指标加载失败 | 保留已成功数据，失败区域显示“数据获取失败，重试” | 将失败值显示为 0 会产生错误经营判断 |
| Tab 快速连续切换 | 只展示最后一次选中 Tab 的结果，并废弃过时请求 | 旧请求后返会覆盖当前 Tab，造成标签与数据不一致 |
| 时间切换中同时导出 | 导出按点击时已确认的 Tab 和时间条件执行 | 使用界面未完成更新的中间参数会导出错误口径 |
| 订单数与资金数不能一一对齐 | 使用节点下的说明文案标明统计口径，不强行用比例画成相等数量 | 将订单数与金额当作同单位会制造虚假流量关系 |
| 退款或售后跨统计周期 | 按退款确认时间冲减当期，异常摘要标注调整额 | 按原订单时间回写历史周期会让已导出报表发生不可解释的变化 |

## 9. 层次与责任边界

| 层次 | 职责 |
|---|---|
| 表现层 | 呈现双 Tab、紧凑指标卡、双轨图、异常摘要和排行表 |
| 业务层 | 按 `channel_type` 和时间范围计算有效订单、成本、结算、回款、余额与异常口径 |
| 数据层 | 继续使用共用企业、订单、采购、账户和结算数据；不为合并页新增第二套表 |
| 基础设施层 | 未来真实实现负责报表查询、缓存、导出任务和可观测性；不在本次静态原型范围内 |

多租户边界：该页是平台运营后台的聚合报表，只允许有相应统计菜单权限的平台内部账号访问。客户侧账号不得通过 Tab 或参数获取其他企业数据。

## 10. 静态原型实施范围

### 10.1 本次实施

- 左侧菜单合并为“渠道经营分析”。
- 新增客户类型 Tab 及可点击切换交互。
- 指标区改为 2 列 × 4 行紧凑布局。
- 使用 HTML/CSS 实现双轨闭环图，不引入第三方图表库。
- 保留两个渠道现有指标和排行数据。
- 同步更新 PRD、静态合约测试和 Playwright 可视检查。

### 10.2 不在本次范围

- 真实报表 API、数据库聚合、缓存或导出任务。
- 指标或异常节点的真实订单下钻。
- 跨渠道汇总 Tab。
- 新增企业、商品分类、供货平台或结算方式筛选。
- 修改客户、订单、积分、采购、结算和售后领域模型。

## 11. 验收标准

1. “经营看板”下仅存在“经营总览”和“渠道经营分析”，不再存在两个旧分析菜单项。
2. 进入合并页默认选中“小程序商城客户”。
3. 页面顶部同时展示两个客户类型 Tab，活动 Tab 在视觉和 `aria-selected` 上都可识别。
4. 点击 API Tab 后，页面出现“采购成功率”和“余额差异”，不展示“消费积分”和“冻结积分”。
5. 再切回小程序 Tab 后，指标、双轨图和排行表恢复小程序口径。
6. 指标区占首屏摘要区左侧，为 2 列 × 4 行；双轨图占右侧主要宽度。
7. 双轨图同时存在“订单流”、“资金流”和异常摘要，且两个 Tab 使用各自的节点名称。
8. 时间选择和导出按钮保留；切换 Tab 不重置当前时间范围。
9. 商品销量排行和企业贡献排行保留，且随 Tab 切换口径。
10. 1440px 与 1024px 视口下页面无横向溢出、节点文案遮挡或指标卡重叠。
11. Tab 支持键盘聚焦，按钮保留可见焦点样式；双轨图不依赖颜色作为唯一信息。
12. 静态合约测试与 Playwright 可视检查通过，浏览器无 JavaScript 运行错误。

## 12. 设计自检结论

- 无 `TBD`、`TODO` 或未定义占位符。
- 菜单合并与两个客户管理模块的业务隔离不冲突。
- Tab 只切换报表查询口径，不修改任何领域状态。
- 双轨图明确为聚合视图，不把订单的并行状态误建模为单链路。
- 原型实施范围与真实后端能力边界已分开，不将静态交互描述为已上线报表服务。
