# 商城订单与 API 订单状态快捷页签设计

- 日期：2026-08-14
- 状态：方案已确认，原型已实施
- 适用范围：平台后台 `小程序商城客户 / 商城订单`、`API供货客户 / API订单`

## 1. 目标与边界

在商城订单和 API 订单列表顶部增加按聚合订单状态划分的快捷页签，帮助运营快速切换主要工作队列。

快捷页签只提供查询视图，不替代积分、接口受理、采购、履约和售后等底层并行状态，也不改变订单状态机、订单数据结构或历史订单。

## 2. 页面结构

订单列表页面按以下顺序展示：

1. 灰色页面说明词及导出等页面操作。
2. 订单状态快捷页签。
3. 订单查询表单。
4. 订单表格和分页。

查询表单移除与快捷页签重复的订单状态下拉框，只保留订单号、客户/企业、商品等查询字段以及“查询”“重置”。

## 3. 快捷页签

商城订单和 API 订单使用同一组页签：

```text
全部｜待处理｜待发货｜已发货｜已完成｜售后/异常
```

- 首次进入页面默认选中“全部”。
- 每个页签显示当前查询范围内的订单数量。
- 当前页签使用明确的选中态。
- 点击页签后立即刷新订单列表，并将页码重置为第 1 页。
- 点击“全部”取消聚合订单状态限制。

## 4. 聚合状态计算

一笔订单只能命中一个快捷页签。系统按以下优先级从高到低计算聚合状态：

| 优先级 | 聚合状态 | 命中条件示例 |
|---|---|---|
| 1 | 售后/异常 | 售后处理中、退款处理中、采购失败、待重试或其他明确失败状态 |
| 2 | 待处理 | 采购结果未知、订单处理中、等待人工确认或等待上游明确结果 |
| 3 | 待发货 | 采购已受理或成功，但尚未发货 |
| 4 | 已发货 | 已产生发货结果，但履约尚未完成 |
| 5 | 已完成 | 履约完成且不存在售后或异常状态 |

“全部”不是订单状态，仅表示不附加聚合状态条件。

高优先级状态覆盖低优先级状态。例如，已完成订单发生退款后进入“售后/异常”，不继续计入“已完成”。

## 5. 两类渠道的状态来源

### 5.1 商城订单

聚合计算读取积分状态、采购状态、履约状态和售后状态。积分冻结或扣减本身不直接决定页签；只有导致订单等待处理或异常的积分结果才影响聚合状态。

### 5.2 API 订单

聚合计算读取接口受理状态、采购状态、履约状态和售后状态。API 接口已受理但采购结果未知时进入“待处理”，采购失败或待重试时进入“售后/异常”。

## 6. 数量统计与查询联动

- 页签数量使用与当前页面相同的渠道、客户/企业、时间和关键词查询条件统计，但不受当前选中聚合状态限制。
- 点击“查询”时保留当前页签，并更新列表和全部页签数量。
- 点击“重置”时清空查询表单、保留当前页签，并从第 1 页刷新。
- 点击其他页签时保留查询表单中的其他条件。
- 页签数量查询失败时显示 `--`，列表仍按当前页签查询；不得把失败数量显示为 0。

## 7. 接口语义

订单列表查询增加展示层参数：

```text
aggregate_status = ALL | PENDING | TO_SHIP | SHIPPED | COMPLETED | AFTER_SALE_OR_EXCEPTION
```

订单列表响应或独立统计接口返回：

```text
status_counts.all
status_counts.pending
status_counts.to_ship
status_counts.shipped
status_counts.completed
status_counts.after_sale_or_exception
```

`aggregate_status` 是查询派生条件，不写入订单主表。正式系统应在服务端使用统一规则计算，前端不得分别实现两套状态映射。

## 8. 原型实现范围

- 商城订单和 API 订单使用同一页签组件和聚合状态配置。
- 原型根据静态订单样例计算页签数量并过滤列表。
- 页签切换、查询和重置均提供真实交互反馈。
- 其他查询列表页面不增加页签。
- 不调整小程序订单页面。

## 9. 验收标准

1. 商城订单和 API 订单页面均展示六个状态快捷页签。
2. 首次进入默认选中“全部”，并展示全部订单。
3. 每个页签显示对应数量，数量合计与“全部”一致。
4. 点击页签后列表只显示对应聚合状态订单，页码回到第 1 页。
5. “待处理”和“售后/异常”能够区分结果未知与明确失败订单。
6. 查询和重置保留当前页签，点击“全部”才取消状态限制。
7. 查询表单中不再出现重复的订单状态下拉框。
8. 底层并行订单状态字段和状态机不变。
