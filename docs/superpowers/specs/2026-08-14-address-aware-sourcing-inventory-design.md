# 集采商品地址化库存查询与下单校验设计

- 日期：2026-08-14
- 状态：方案已确认，待 PRD 与原型实施
- 适用范围：拾马商城后台商品库、供货平台来源商品、小程序商城订单、API 供货订单

## 1. 业务目标

集采平台的商品库存会随实际收货地区变化，平台不能继续将某个地区的库存结果作为全国统一库存展示或用于下单。

本需求需要形成以下闭环：

1. 后台按运营选择的收货地区查询并展示集采商品库存。
2. 小程序和 API 客户提交订单时，按订单实际收货地址强制查询实时库存。
3. 实时库存充足后才允许创建订单并冻结积分、预存款或占用授信额度。
4. 每次查询结果写入地址维度的库存快照，供商品库在相同地区上下文中展示。
5. 缓存库存只能用于页面展示，不能作为最终下单依据。

成功标准：

- 集采商品订单提交前实时库存校验覆盖率为 100%。
- 不存在使用其他地区库存或过期库存放行订单的情况。
- 库存接口返回超时、未知结果或地址不可识别时，不创建订单且不冻结资产。
- 相同 SKU 在不同地区的查询结果相互隔离，不发生覆盖。

核心用户故事：

| 使用方 | 用户故事 |
|---|---|
| 平台运营 | 选择一个收货地区后查看集采 SKU 在该地区的最近库存，不把地区库存误认为全国库存 |
| 小程序客户 | 使用最终收货地址提交兑换时，缺货或不可配送商品不能生成订单或冻结积分 |
| API 客户 | 提交带实际收货地址的订单时，获得明确的库存受理或拒绝结果，失败时不占用余额或授信 |
| 平台财务/客服 | 可以通过库存校验记录定位订单为何被拒绝或采购为何在校验后仍失败 |

## 2. 核心业务边界

### 2.1 集采商品

- 集采商品不存在可直接用于全部地区的“全局可售库存”。
- 库存查询维度为：供货平台、来源 SKU、标准化收货地区。
- 标准化收货地区至少包含省、市、区/县；供货平台要求街道/乡镇 ID 时必须继续传递第四级地址编码。
- 商品库中的库存是指定地区下最近一次查询结果的展示投影，不回写为平台商品的全局库存。
- 最新成本价仍按来源 SKU 维护，不受收货地址影响；如果后续供货平台出现地区价，则另行扩展地区价格模型。

### 2.2 自营商品

- 自营商品继续使用平台本地库存，不要求选择地区后查询。
- 下单时通过本地库存服务完成原子预占，不能套用集采平台地址库存接口。

### 2.3 缓存与实时结果

- 后台按地区执行普通查询时可使用 5 分钟内的同地区库存快照，页面必须标明地区、查询时间和“缓存结果”。
- 快照过期、无快照，或运营点击库存结果旁的“重新查询”时调用供货平台库存接口，并标明“实时结果”。
- 订单最终提交必须设置 `force_refresh=true`，绕过库存快照调用供货平台。
- 实时查询失败时，旧快照可以继续用于后台参考，但必须标记“已过期/查询失败”，不得用于放行订单。

## 3. 总体分层

### 3.1 表现层

- 后台商品管理：选择库存地区，查询平台商品列表中的集采库存。
- 供货平台来源商品：选择库存地区，查看来源 SKU 的地址库存。
- 小程序：根据结算页最终收货地址完成库存预校验；提交订单时由服务端再次强校验。
- API 供货：订单接口接收实际收货地址，由服务端在受理订单前强校验。

### 3.2 业务层

统一 `InventoryService` 负责：

- 地址标准化与供货平台地址 ID 转换。
- 按供货平台拆分 SKU 查询任务。
- 区分 `DISPLAY` 和 `ORDER_SUBMIT` 两种查询模式。
- 统一解析数量型、有无货型和不可配送型库存结果。
- 写入地址库存快照。
- 向订单服务返回可下单结论和结构化失败原因。

小程序订单与 API 订单必须复用同一套库存校验服务，不能各自实现不同规则。

### 3.3 集成层

每个供货平台适配器实现统一能力：

```text
queryInventory(supplierSkuIds, supplierAddressIds, requestContext)
```

适配器负责鉴权、地址字段组装、批量限制、超时、重试和供应商错误码转换。库存查询为只读操作，可以在明确超时且未取得结果时重试。

### 3.4 数据层

库存快照与平台商品、来源商品分开存储。平台商品只通过来源关系读取相应地址快照，不增加全局集采库存字段。

## 4. 数据结构

### 4.1 地址库存快照

```text
supplier_inventory_snapshot
├── id
├── supplier_id
├── supplier_product_id
├── supplier_sku_id
├── platform_sku_id
├── region_key
├── province_code
├── city_code
├── district_code
├── town_code
├── supplier_address_id_path
├── stock_result_type        QUANTITY / BOOLEAN
├── available_quantity       数量型结果；有无货型为空
├── availability_status      IN_STOCK / OUT_OF_STOCK / UNSERVICEABLE / UNKNOWN
├── queried_at
├── expires_at
├── supplier_response_code
├── correlation_id
└── updated_at
```

唯一约束：

```text
(supplier_id, supplier_sku_id, region_key)
```

`region_key` 由标准化省、市、区/县、街道/乡镇编码生成。同一 SKU 在长沙和北京的快照必须是两条独立记录。

库存快照不保存收件人姓名、手机号、门牌号等个人信息。供货平台库存接口确需完整地址时，完整地址只在当前请求链路中传递，不进入库存快照。

### 4.2 供货平台地址映射

```text
supplier_region_mapping
├── supplier_id
├── platform_region_code
├── platform_region_level
├── supplier_region_id
├── mapping_status           ACTIVE / INVALID
├── synced_at
└── updated_at
```

平台标准地区与供货平台地址 ID 分开维护。映射缺失时，可以调用供货平台地址接口即时获取并保存；获取失败时返回地址不可识别，不能使用其他地区兜底。

### 4.3 订单库存校验记录

```text
order_inventory_check
├── id
├── request_id
├── order_id                 校验失败且未创建订单时可为空
├── channel_type             MINIAPP / API
├── enterprise_id
├── supplier_id
├── supplier_sku_id
├── region_key
├── requested_quantity
├── available_quantity
├── check_result             PASSED / REJECTED / ERROR
├── failure_code
├── supplier_response_code
├── correlation_id
└── checked_at
```

该记录用于证明订单提交前确实执行过实时库存校验，不替代库存快照和订单状态。

## 5. 后台页面设计

### 5.1 商品管理

商品管理继续保持左侧分类树、右侧统一商品列表，不增加新的库存菜单。

查询表单增加级联字段“库存地区”：省、市、区/县；供货平台要求第四级地址时继续选择街道/乡镇。查询表单仍只保留“查询、重置”按钮。

库存列规则：

| 商品来源 | 未选择地区 | 已选择地区 |
|---|---|---|
| 自营 | 展示平台本地可售库存 | 仍展示平台本地可售库存 |
| 集采 | 显示“需选择地区查询” | 展示该地区库存状态、数量和查询时间 |

数量型接口展示“可用 568”；有无货型接口只展示“有货/无货”，不得推断数量。

库存结果需要同时展示：

- 当前地区，例如“湖南省 / 长沙市 / 岳麓区”。
- 实时结果或缓存结果。
- 最近查询时间。
- 已过期、查询失败或不支持配送状态。

缓存结果旁提供“重新查询”行内入口，用于绕过展示缓存刷新当前 SKU；该入口属于库存结果操作，不放入顶部查询表单。

点击“重置”清空库存地区，集采库存恢复为“需选择地区查询”；左侧当前商品分类继续保留。

### 5.2 供货平台来源商品

来源商品页面同样增加库存地区级联字段。未选择地区时不再展示来源 SKU 的全局数量，显示“需选择地区查询”。

查询后只展示当前供货平台、当前来源 SKU、当前地区的结果。实时查询结果同步写入地址库存快照，商品管理选择相同地区时可以读取该结果。

## 6. 小程序订单流程

### 6.1 结算页预校验

用户选定或修改收货地址后，系统按实际地址查询集采 SKU 库存和配送能力，及时提示无货或不支持配送。该结果用于结算页反馈，不代表最终库存锁定。

### 6.2 提交订单强校验

```text
接收提交请求
→ 校验企业、商品、SKU和收货地址
→ 标准化地址并转换供货平台地址ID
→ 按供货平台实时查询库存
→ 全部集采SKU库存充足
→ 在同一业务事务中创建平台订单并冻结对应积分
→ 发起上游采购
```

只要任一集采 SKU 校验失败，整单不创建且不冻结积分。库存通过后如果积分冻结失败，则回滚订单创建；第一期不做缺货商品自动拆单。

库存校验通过后仍可能在上游采购时发生并发售罄。此时订单进入采购失败状态，释放已冻结积分，并保留库存校验和采购失败记录。

## 7. API 订单流程

API 客户提交订单时必须传递结构化收货地区编码和详细地址。服务端不能使用客户账户默认地区替代订单实际地址。

```text
API订单请求
→ 幂等校验
→ 地址完整性与地区映射校验
→ 实时库存校验
→ 库存充足后在同一业务事务中创建订单并占用预存余额或授信
→ 返回订单受理结果
```

库存不足、地址不可配送、地址映射失败或库存接口异常时，同步拒绝本次订单请求，不创建业务订单，也不占用余额或授信。

可以向 API 客户提供库存预查询接口，但预查询结果不构成库存承诺；正式订单接口仍必须重新实时校验。

## 8. 状态与错误码

页面库存状态：

```text
NEED_ADDRESS
→ QUERYING
→ IN_STOCK / OUT_OF_STOCK / UNSERVICEABLE
→ STALE               快照过期
→ QUERY_FAILED        实时查询失败
```

订单校验结果：

```text
CHECKING
→ PASSED
→ REJECTED            库存不足或不可配送
→ ERROR               地址或供应商接口异常
```

统一错误码：

| 错误码 | 含义 | 是否允许创建订单 |
|---|---|---|
| `ADDRESS_REQUIRED` | 缺少收货地址 | 否 |
| `ADDRESS_MAPPING_FAILED` | 无法转换供货平台地址 ID | 否 |
| `REGION_UNSERVICEABLE` | 当前地区不支持配送 | 否 |
| `INVENTORY_INSUFFICIENT` | 可用库存不足 | 否 |
| `INVENTORY_TIMEOUT` | 库存接口超时 | 否 |
| `INVENTORY_RESULT_UNKNOWN` | 供货平台未返回明确结果 | 否 |

## 9. 接口设计

### 9.1 后台库存查询

```http
POST /admin/products/inventory/query
```

请求包含标准化地区编码和当前列表 SKU；服务端按供货平台分组并批量查询。响应按平台 SKU 返回数量或有无货状态、结果来源、查询时间和错误码。

### 9.2 小程序库存预校验

```http
POST /miniapp/inventory/check
```

用于结算页地址变化后的预校验。正式 `POST /miniapp/orders` 内部仍必须执行 `ORDER_SUBMIT` 模式强校验。

### 9.3 API 客户库存预查询

```http
POST /openapi/v1/inventory/check
```

该接口为可选能力，返回结果必须带查询时间，并明确“下单时重新校验”。正式订单接口必须包含幂等键和实际收货地址。

### 9.4 内部调用模式

```text
InventoryService.check(items, address, mode)

mode=DISPLAY
  允许读取5分钟内同地区快照
  forceRefresh=true时绕过展示缓存

mode=ORDER_SUBMIT
  强制请求供货平台
  任何不明确结果均返回不可下单
```

## 10. 性能、重试与幂等

- 后台列表按当前页 SKU 查询，不一次查询全商品库。
- SKU 按供货平台分组，并遵守各平台批量查询上限。
- 展示查询可在超时后重试最多 2 次；订单强校验只允许在总体超时时间内对明确的可重试错误重试，超出后阻断下单。
- 单个平台故障不能将其他平台结果覆盖为空；页面逐平台展示成功或失败结果。
- API 订单使用客户订单号和企业 ID 做幂等控制；重复请求复用首次业务结果，不重复冻结资产或创建订单。
- 库存查询使用 `correlation_id` 串联地址转换、库存请求、订单校验和上游采购日志。

## 11. 异常与边界

| 场景 | 处理 |
|---|---|
| 后台未选择地区 | 集采库存显示需选择地区，不请求接口 |
| 同一 SKU 查询两个地区 | 分别保存两条快照，不互相覆盖 |
| 快照仍有效 | 后台可展示缓存结果并标注查询时间 |
| 快照过期且实时查询失败 | 展示旧值并标记已过期；订单不可使用 |
| 供货平台只返回有无货 | 只展示状态，不伪造数量 |
| 收货地区不支持配送 | 返回不可配送，不尝试其他地区兜底 |
| 多商品订单中一个 SKU 缺货 | 整单拒绝，不创建订单、不冻结资产 |
| 库存校验后上游并发售罄 | 采购失败，释放冻结资产并记录失败原因 |
| 自营与集采混合订单 | 自营执行本地预占，集采执行地址实时校验；任一失败则整单不创建 |
| 下单重复请求 | 返回首次幂等结果，不重复校验后创建第二张订单 |

## 12. 一期范围

一期必做：

- 后台商品管理和来源商品页的库存地区选择。
- 地址维度库存快照。
- 小程序订单和 API 订单提交前实时库存强校验。
- 库存异常时阻断下单和资产冻结。
- 查询日志、校验记录和统一错误码。

一期暂不做：

- 预占或锁定集采平台库存。
- 缺货商品自动拆单或切换其他供货平台。
- 按热门地区定时预热全部商品库存。
- 将某个地区库存汇总为全国库存。
- 地区差异价格模型。

一期开发量级：

| 工作项 | 优先级 | 量级 |
|---|---|---|
| 供货平台地址映射与库存适配器 | MVP 必做 | L；多平台协议差异最大 |
| 地址库存快照与统一库存服务 | MVP 必做 | M |
| 小程序与 API 订单强校验、资产事务 | MVP 必做 | M |
| 后台商品管理和来源商品地址库存交互 | MVP 必做 | M |
| 日志、错误码、幂等与自动化测试 | MVP 必做 | M |
| 热门地区库存预热、自动拆单、替代供货 | 可延后 | L |

## 13. 验收标准

1. 集采商品在未选择库存地区时不展示全局库存数量。
2. 后台选择地区后，只展示该地区的库存结果、结果来源和查询时间。
3. 同一 SKU 的不同地区库存快照独立保存。
4. 小程序和 API 订单均使用订单实际收货地址进行实时校验。
5. 订单强校验绕过缓存；缓存只用于后台和结算页参考。
6. 库存不足、不可配送、地址映射失败、接口超时或结果未知时不创建订单、不冻结积分、不占用余额或授信。
7. 数量型和有无货型供货平台结果均能正确展示，不虚构数量。
8. 实时结果同步到相同地区的商品库库存展示，但不覆盖其他地区，也不写成平台全局库存。
9. 自营商品继续使用本地库存，不受集采地址库存逻辑影响。
10. 库存校验通过后采购仍失败时，系统释放冻结资产并保留完整失败记录。
