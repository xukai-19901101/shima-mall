# 拾马商城后台系统管理与菜单权限设计

- 日期：2026-08-14
- 状态：方案已确认，原型已实施
- 适用范围：拾马商城平台内部后台

## 0. 需求变更声明

本规格以 2026-08-14 最新确认为准，覆盖一期 PRD 中“平台后台一期不区分操作角色”以及既有设计中“不增加后台角色和权限体系”的旧结论。实施时必须同步修订旧条目，避免研发按冲突版本执行。

## 1. 业务目标

为拾马商城平台内部运营人员提供独立后台账号，并通过角色控制其可见、可访问的后台菜单，降低所有人员共用平台账号造成的误操作风险。

本功能只管理平台内部后台账号，不包含小程序客户、API 客户及其下游终端用户。

## 2. 一期范围

### 2.1 包含

- 用户管理：新建、编辑、启用、停用、重置密码、分配角色。
- 角色权限：新建、编辑、启用、停用、配置菜单权限。
- 单用户单角色。
- 内置超级管理员角色。
- 登录后按角色生成菜单，并校验页面访问权限。

### 2.2 不包含

- 页面按钮权限。
- 数据范围权限。
- 单用户多角色。
- 部门、岗位和组织架构。
- 小程序客户或 API 客户账号管理。
- 角色硬删除与用户硬删除。

## 3. 菜单结构

```text
系统管理
├── 用户管理
└── 角色权限
```

“系统管理”作为后台一级模块，放在侧边导航末尾；“用户管理”和“角色权限”作为其二级菜单。

## 4. 对象关系

```text
后台用户 N ── 1 角色
角色 1 ── N 菜单权限
菜单权限 N ── 1 后台菜单
```

- 一个后台用户必须绑定一个启用中的角色。
- 一个角色可以绑定多个后台用户。
- 一个角色可以配置多个模块和二级菜单。
- 用户最终菜单集合完全来自其角色，不允许在用户上追加或覆盖菜单权限。

## 5. 用户管理

### 5.1 页面结构

页面遵循后台统一查询列表规范：

1. 灰色页面说明与右侧“新建用户”。
2. 查询表单。
3. 用户列表与分页。

查询字段：用户姓名、登录账号、所属角色、状态。

列表字段：用户姓名、登录账号、手机号、所属角色、状态、最后登录时间、创建时间、操作。

操作入口：

- 新建用户。
- 编辑用户。
- 启用或停用用户。
- 重置密码。

### 5.2 用户表单

| 字段 | 必填 | 规则 |
|---|---:|---|
| 用户姓名 | 是 | 2—20 个字符 |
| 登录账号 | 是 | 全局唯一；创建后不可修改 |
| 手机号 | 否 | 填写时校验手机号格式 |
| 所属角色 | 是 | 只能选择启用中的角色 |
| 初始密码 | 新建时是 | 不在列表或详情中明文展示 |
| 状态 | 是 | 启用、停用 |

### 5.3 用户状态

```text
新建并启用 → 启用
新建并停用 → 停用
启用 ──停用──> 停用
停用 ──启用──> 启用
```

- 用户停用后禁止新登录，已有登录状态失效。
- 用户重新启用后可使用原账号登录；密码仍采用最近一次重置结果。
- 不提供硬删除，避免历史操作记录失去责任主体。

## 6. 角色权限

### 6.1 页面结构

页面遵循后台统一查询列表规范：

1. 灰色页面说明与右侧“新建角色”。
2. 查询表单。
3. 角色列表与分页。

查询字段：角色名称、状态。

列表字段：角色名称、角色说明、关联用户数、已授权菜单数、状态、更新时间、操作。

操作入口：新建角色、编辑角色、启用或停用角色、配置菜单权限。

### 6.2 角色表单

| 字段 | 必填 | 规则 |
|---|---:|---|
| 角色名称 | 是 | 平台内部唯一 |
| 角色说明 | 否 | 说明适用岗位或职责 |
| 状态 | 是 | 启用、停用 |
| 菜单权限 | 是 | 至少选择一个可访问二级菜单 |

### 6.3 菜单权限树

- 按后台一级模块和二级菜单展示完整菜单树。
- 勾选一级模块时，全选其下二级菜单。
- 取消一级模块时，取消其下全部二级菜单。
- 只勾选部分二级菜单时，一级模块显示半选状态。
- 保存时以二级菜单授权为准；一级模块是导航分组，不单独形成可访问页面。
- 角色权限发生变化后，关联用户下一次页面请求重新获取菜单；已失去权限的当前页面跳转至首个有权菜单。

### 6.4 角色状态

- 停用角色前必须二次确认，并提示受影响用户数。
- 角色停用后，关联用户禁止登录，已有登录状态失效。
- 停用角色不能分配给新用户。
- 角色重新启用后，原有关联用户恢复登录资格。
- 不提供角色硬删除；无关联用户的普通角色也只允许停用。

## 7. 超级管理员

- 系统内置一个“超级管理员”角色，自动拥有全部当前及未来新增菜单。
- 超级管理员角色不可停用、删除或修改菜单权限。
- 至少保留一个启用中的超级管理员用户。
- 最后一个启用中的超级管理员用户不可停用，也不可改为其他角色。
- 超级管理员可以维护其他后台用户和普通角色。

## 8. 权限校验链路

```text
用户提交账号密码
→ 校验用户状态
→ 校验所属角色状态
→ 加载角色菜单权限
→ 返回用户信息与可见菜单
→ 前端生成侧边导航
→ 用户访问页面时后端再次校验菜单权限
```

- 前端隐藏菜单只用于界面呈现，不能作为安全边界。
- 后端必须根据当前用户角色校验页面对应权限编码。
- 未授权访问返回无权限结果；前端展示提示并跳转至首个有权限的菜单。
- 无任何可用菜单的普通角色不允许保存，避免产生无法正常进入后台的用户。

## 9. 最小数据结构

| 对象 | 核心字段 |
|---|---|
| `admin_user` | `id`、`login_name`、`display_name`、`mobile`、`password_hash`、`role_id`、`status`、`last_login_at`、`created_at`、`updated_at` |
| `admin_role` | `id`、`role_name`、`description`、`status`、`is_super_admin`、`created_at`、`updated_at` |
| `admin_menu` | `id`、`parent_id`、`menu_name`、`permission_code`、`route`、`sort`、`status` |
| `admin_role_menu` | `role_id`、`menu_id`、`created_at` |

约束：

- `admin_user.login_name` 全局唯一。
- `admin_user.role_id` 必填。
- `admin_role.role_name` 全局唯一。
- `admin_role_menu(role_id, menu_id)` 联合唯一。
- `permission_code` 全局唯一且不随菜单名称修改而变化。

## 10. 存量迁移

- 将现有“平台账号”迁移为首个超级管理员用户。
- 初始化现有全部一级模块和二级菜单到菜单表。
- 普通角色由超级管理员在系统管理中新增并授权。
- 迁移完成前不切换登录鉴权逻辑；切换失败时可回退至原平台账号登录。

## 11. 异常与边界

| 场景 | 处理 |
|---|---|
| 登录账号重复 | 阻止保存并提示账号已存在 |
| 角色名称重复 | 阻止保存并提示角色名称已存在 |
| 给用户选择停用角色 | 不允许选择或保存 |
| 普通角色未选择任何二级菜单 | 阻止保存 |
| 停用有关联用户的角色 | 二次确认，确认后角色及关联用户会话失效 |
| 停用最后一个超级管理员用户 | 阻止操作 |
| 普通用户访问未授权路由 | 返回无权限并跳转至首个有权菜单 |
| 菜单权限保存失败 | 保留编辑内容并提示失败，不覆盖原权限 |
| 并发修改同一角色 | 使用更新时间或版本号校验，冲突时提示刷新后重试 |

## 12. 验收标准

1. 后台侧边导航新增“系统管理”，包含“用户管理”和“角色权限”。
2. 用户可完成新建、编辑、启停、重置密码和单角色分配。
3. 角色可完成新建、编辑、启停和菜单树授权。
4. 用户登录后只看到所属角色已授权的菜单。
5. 未授权页面无法通过直接地址访问。
6. 用户或角色停用后，关联登录状态失效。
7. 超级管理员始终拥有全部菜单，且不可被停用或减少权限。
8. 一期不出现按钮权限、数据范围权限、多角色或组织架构配置。
